# ADR-013: Portuguese as Third Locale by Extending LocaleProvider

**Status**: Accepted
**Date**: 2026-07-05
**Branch**: `feature/pt-locale`
**Feature**: `docs/specs/FEATURE-10_PT_LOCALE/spec.md`
**Supersedes**: —
**Related**: ADR-006, ADR-010, ADR-011

---

## Context

The portfolio currently serves two URL-addressable locales:

| Locale | URL prefix | Role |
|--------|------------|------|
| `es` | `/` | Canonical default |
| `en` | `/en` | International variant |

FEATURE-10 adds Portuguese as a third locale at `/pt` to support Brazilian,
Portuguese, and broader lusophone visitors. The existing i18n architecture from
FEATURE-01 already provides the required primitives:

- React Router derives the locale from the URL
- `LocaleProvider` receives the locale as a prop
- `useLocale()` exposes `{ locale, t }` to shared components
- Locale content is stored in plain JavaScript files by section
- Route components are shared between locales instead of duplicated

The feature does not require a new i18n framework, a runtime locale store, or a
different routing model.

---

## Decision

Add Portuguese by extending the existing locale map and route tree.

- Portuguese is served at `/pt` and all sub-paths (`/pt/blog`,
  `/pt/proyecto/:id`, `/pt/agencias`, `/pt/blog/:slug`)
- `LocaleLayout` recognizes `/pt` and passes `locale="pt"` to
  `LocaleProvider`
- `LocaleProvider` imports `src/locales/pt/*.js` and adds a `pt` entry to the
  existing `localeFiles` object
- `projects.pt.js` and `blogData.pt.js` mirror the slugs and data contracts of
  the existing ES/EN files
- `LangSwitcher` evolves from a two-locale toggle to a three-locale selector,
  while preserving URL-derived locale state
- No new external dependencies are introduced
- No browser storage is used; ADR-011 remains authoritative
- `vercel.json` is unchanged because the existing catch-all rewrite covers
  `/pt/*`

The Portuguese route segment for agencies is `agencias`, matching Spanish:
`/pt/agencias`.

---

## Consequences

**Positive**:
- The third locale reuses the proven architecture from FEATURE-01
- Route behavior remains deterministic and shareable because the URL is still
  the only source of locale state
- Components continue to be locale-agnostic and consume `useLocale()`
- SEO and `hreflang` can represent ES, EN, and PT as distinct crawlable pages
- The implementation remains dependency-free and easy to inspect

**Negative / Trade-offs**:
- `LangSwitcher` becomes more complex because segment translation is no longer
  a simple ES/EN pair
- Every locale-keyed data source must now keep three files structurally aligned
- Manual validation grows from two locale transitions to six transition pairs

**Neutral**:
- Spanish remains canonical at `/`; Portuguese does not change canonical
  hierarchy
- The `/pt/agencias` segment intentionally duplicates the ES segment because
  `agencias` is valid Portuguese and avoids an artificial route translation

---

## Alternatives Rejected

**Introduce an i18n library**: Rejected. The project already has a small,
explicit locale architecture that handles the required URL-based behavior. A
library would add dependency and configuration surface without reducing the core
work of translating content and routes.

**Duplicate page components for PT**: Rejected. Duplicating pages by locale
would create maintenance drift and conflict with the shared component model from
FEATURE-01.

**Use `localStorage` to remember PT preference**: Rejected by ADR-011. Locale is
a content dimension encoded in the URL, not a client preference.

**Use a different PT segment for agencies**: Rejected after product
confirmation. `/pt/agencias` is clear for lusophone users and keeps the route
compact.
