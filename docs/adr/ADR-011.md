# ADR-011: URL as Single Source of Truth for Locale State

**Status**: Accepted
**Date**: 2026-06-05
**Branch**: `feature/seo-aeo-i18n-button`
**Feature**: `specs/features/001-i18n-url-routing/spec.md`
**Supersedes**: —
**Related**: ADR-006, ADR-007, ADR-010

---

## Context

In any stateful locale system, one component must own the locale value. The candidates are:

| Storage Mechanism | Persistence | Crawlable | Shareable | Deterministic |
|-------------------|-------------|-----------|-----------|---------------|
| `localStorage` | Session + beyond | ❌ | ❌ | ❌ |
| `sessionStorage` | Tab lifetime | ❌ | ❌ | ❌ |
| React state (in-memory) | Component lifetime | ❌ | ❌ | ❌ |
| Cookie | Configurable | ❌ (CSR) | ❌ | ❌ |
| **URL path prefix** | Permanent (in the URL) | ✅ | ✅ | ✅ |

The architecture established in ADR-006 makes URL-based routing the locale delivery mechanism. This ADR establishes the complementary constraint: **no other mechanism may write or read locale state**.

The specific risk being mitigated is `localStorage` persistence. A common pattern in locale toggles is: "remember the user's last language choice." This creates a split-brain problem:

1. A user visits `/` (English canonical)
2. They switch to Spanish — `localStorage.locale = "es"` is written
3. They share the URL `/` with a colleague
4. The colleague lands on Spanish because `localStorage` overrides the URL
5. The colleague's experience is non-deterministic — it depends on whether they have a `localStorage` value

This behavior is unacceptable for a portfolio where shared links are a conversion path. The URL must be the complete, self-contained description of the page's state.

---

## Decision

The URL path is the sole mechanism for determining and communicating locale. Specifically:

- The `LocaleContext` value is derived **only** from the React Router pathname at render time
- No `localStorage`, `sessionStorage`, cookie, or in-memory state outside the URL may influence the locale
- The `LangSwitcher` component changes locale **only** by navigating to a new URL — it does not call `setState`, write to storage, or modify any global variable
- If a user navigates directly to `/` (e.g., by clicking the site logo), they receive English — regardless of any prior locale preference
- The logo `href` in `Header.jsx` resolves to the locale root of the current session: `/` if on an EN route, `/es` if on an ES route — computed from `pathname`, not from stored state

---

## Consequences

**Positive**:
- Every URL is a complete, deterministic description of its page — including language
- Shared links always deliver the intended language to the recipient
- Crawlers receive consistent, reproducible responses — no session variance
- Debugging is trivial: the URL tells you everything about the page state
- Zero browser storage API calls — cleaner privacy posture

**Negative / Trade-offs**:
- Users who prefer Spanish must use the `/es` URL or click the switcher on every new entry point. There is no "remember my preference" functionality. Mitigation: the `LangSwitcher` is persistent in the header across all routes, making it a one-click action from any page
- Deep-linking to a Spanish page requires knowing or discovering the `/es` prefix. Mitigation: the `LangSwitcher` is the discovery mechanism; no additional onboarding is needed

**Neutral**:
- This constraint aligns with the stateless SPA philosophy already present in the codebase (no Redux, no Zustand, no global state management library)
- The `LocaleProvider` remains a pure function of its `locale` prop — straightforward to test, straightforward to reason about

---

## Alternatives Rejected

**`localStorage` persistence**: Rejected. Creates non-deterministic URL behavior (same URL delivers different languages to different users). Breaks the shareable-link use case. Complicates debugging. Provides no indexability benefit.

**Cookie-based locale**: Rejected for the same determinism reasons as `localStorage`. Additionally, a CSR SPA on Vercel has no server-side cookie reading on the edge for locale resolution without a middleware layer — introducing one would conflict with the Vite CSR architecture.

**`Accept-Language` header detection**: Rejected. Googlebot does not send locale-specific `Accept-Language` headers, making auto-detection unreliable for crawlers. Additionally, it would introduce a redirect or JavaScript detection step that conflicts with the URL-as-source-of-truth principle.

**In-memory React state at app root**: Rejected. Locale state in React state is reset on every page refresh, creating a poor user experience on direct navigation. It also provides no crawlability benefit.
