# ADR-010: No External i18n Library — Plain JS Locale Files

**Status**: Accepted
**Date**: 2026-06-05
**Branch**: `feature/seo-aeo-i18n-button`
**Feature**: `specs/features/001-i18n-url-routing/spec.md`
**Supersedes**: —
**Related**: ADR-006, ADR-007, ADR-011
**Consistent with**: ADR-002 (JavaScript over TypeScript — preference for minimal overhead)

---

## Context

Implementing bilingual content requires a mechanism to deliver the correct string to each component based on the active locale. The industry offers mature libraries for this purpose (`react-i18next`, `next-intl`, `lingui`, `formatjs`). The question is whether the portfolio's requirements justify the overhead of introducing one.

The scope of the i18n requirement was evaluated:

- **2 locales** (English, Spanish) — not 10+
- **~60–80 UI strings** across 5 sections — not thousands of keys
- **No pluralization rules** beyond trivial cases
- **No date/number/currency formatting** via i18n — Intl API handles these natively when needed
- **No ICU message format** requirements
- **No runtime locale switching** — locale is always known from the URL at render time (ADR-011)
- **No translation management platform** (Crowdin, Lokalise) — content is authored directly by the developer

Under these constraints, a full i18n library solves problems this project does not have, while adding:
- A runtime dependency with its own API surface to maintain
- Bundle weight (react-i18next: ~13KB gzip)
- An abstraction layer between components and their strings that provides no architectural benefit at this scale

---

## Decision

Locale strings are stored as plain JavaScript object exports in `src/locales/{locale}/{section}.js`. No external i18n library is introduced.

Structure:
```
src/locales/
├── en/
│   ├── common.js      → export default { nav: { works: "Works", ... }, footer: { ... } }
│   ├── hero.js        → export default { title: "...", subtitle: "...", cta: "..." }
│   ├── services.js
│   ├── works.js
│   └── contact.js
└── es/
    └── (mirror structure, Spanish values)
```

The `LocaleProvider` (established in ADR-006) imports the correct locale files based on the active locale and assembles a `t` object passed via context. Components access strings via `const { t } = useLocale()` — a single, consistent API regardless of the underlying storage format.

This design does not preclude migrating to `react-i18next` in the future. The `useLocale()` hook is the only consumer-facing API. If a library is adopted later, only the hook's internals change — zero component rewrites required.

---

## Consequences

**Positive**:
- Zero additional runtime dependencies — consistent with ADR-002 philosophy
- No bundle weight increase beyond the locale files themselves (which are tree-shaken by Vite)
- Full IDE autocompletion on locale objects — no string key lookups at runtime
- Locale files are readable, diffable, and editable without tooling
- Adding a third locale (e.g., `pt` for Brazil) requires creating one new directory — no library configuration

**Negative / Trade-offs**:
- No built-in pluralization — must be handled manually if needed (acceptable at current scale)
- No ICU message format support — interpolation must be done via template literals or a utility function
- No translation memory or missing key warnings out of the box — mitigated by the structural diff check in T-02 (both locale mirrors must have identical key structures)
- If the project grows to 5+ locales or 500+ keys, this approach becomes maintenance-heavy. That threshold triggers a migration to `react-i18next` (documented below)

**Migration trigger**: If any of the following occur, evaluate migration to `react-i18next`:
- Locale count exceeds 3
- Total string count exceeds 300 keys
- A translation management workflow (Crowdin, Lokalise) is required

---

## Alternatives Rejected

**react-i18next**: The most common choice. Rejected because it solves pluralization, ICU format, and namespace loading — none of which are requirements at current scope. The 13KB bundle cost and API complexity are not justified for 2 locales and ~80 strings.

**next-intl**: Designed for Next.js App Router with RSC integration. Architecturally incompatible with a Vite CSR SPA.

**lingui / formatjs**: Powerful, but require a compilation step and message extraction tooling. The setup overhead exceeds the problem scope by a significant margin.
