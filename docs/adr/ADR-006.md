# ADR-006: URL-Based i18n Over Client-Side Locale Toggle

**Status**: Accepted
**Date**: 2026-06-05
**Branch**: `feature/seo-aeo-i18n-button`
**Feature**: `specs/features/001-i18n-url-routing/spec.md`
**Supersedes**: —
**Related**: ADR-007, ADR-010, ADR-011

---

## Context

The portfolio required a bilingual experience (English / Spanish) to serve an international target market (US and Europe) while preserving a Spanish-language fallback for regional visitors.

Three architectural options were evaluated:

| Option | Description | SEO Indexability |
|--------|-------------|-----------------|
| **A — Context Toggle** | `React.createContext` holding locale state, persisted in `localStorage`. Single URL for all languages. | ❌ One URL indexed per page. Googlebot sees only one language per crawl. |
| **B — react-i18next** | Third-party library managing locale state, also single-URL by default unless configured with URL routing. | ❌ Same indexability problem as Option A unless combined with Option C. Adds external dependency. |
| **C — URL-Based Routing** | Locale encoded in the URL path. English at `/`, Spanish at `/es`. Two distinct, crawlable URLs per page. | ✅ Each locale is a separately indexable document. |

The portfolio's primary objective is international lead generation, not a logged-in application with user preferences. Locale is not a user preference in this context — it is a content dimension, equivalent to a different page. URL-based routing is the only option that exposes both language variants as independent, crawlable documents to search engines and AI answer engines.

Additionally, Option C is a prerequisite for correct `hreflang` implementation (Feature 002) and for `areaServed: "Worldwide"` Schema.org signals (Feature 003). Neither can function correctly without two distinct URLs to cross-reference.

---

## Decision

Implement URL-based locale routing using React Router DOM v7 nested routes.

- English is served at the root path `/` and all sub-paths (`/blog`, `/works/:slug`, etc.)
- Spanish is served at `/es` and all sub-paths (`/es/blog`, `/es/works/:slug`, etc.)
- The locale is derived exclusively from the URL at render time
- No external i18n library is introduced (see ADR-010)
- A single route component tree is shared between both locales via `LocaleProvider` — no component duplication

---

## Consequences

**Positive**:
- Both locales are independently indexable by Googlebot, Bingbot, GPTBot, and other crawlers
- `hreflang` tags can reference two distinct canonical URLs (required for Feature 002)
- Sharing a link always delivers the intended language to the recipient — no locale mismatch
- Locale state is stateless and reproducible: any URL uniquely determines its language
- Removes all dependency on browser storage for a non-preference concern

**Negative / Trade-offs**:
- All existing routes effectively double in address space (16 URLs instead of 8)
- `vercel.json` rewrite rules must explicitly cover `/es/*` paths to prevent 404 on direct navigation
- Blog posts without a Spanish translation require a fallback route handler (FR-009)
- LangSwitcher must compute the locale-equivalent path rather than simply toggling a state variable

**Neutral**:
- React Router DOM v7 (already in `package.json`) supports the required nested route pattern with no upgrade
- Framer Motion animations and canvas components (`ParticleBackground`, `WireframeGeometry`) are locale-agnostic and require no changes

---

## Alternatives Rejected

**Option A (Context Toggle)**: Rejected because a single URL indexed in one language provides no SEO benefit for the non-default language. A Spanish visitor finding the site via an English-indexed URL lands in the wrong language with no signal to search engines that a Spanish version exists.

**Option B (react-i18next)**: Rejected on two grounds. First, it introduces an external runtime dependency for a problem solvable with plain JS objects (see ADR-010). Second, it does not inherently solve the indexability problem — it would require URL-based routing configuration regardless, making it an unnecessary abstraction layer over Option C.
